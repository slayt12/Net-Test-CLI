nettest Administrator Guide

Network path troubleshooting with the nettest client and server

Version 1.1.2 · Covers Windows 11 and Linux · October 2026 (revision 4: Microsoft Teams alerts, automatic monitor.toml encoding conversion)

nettest is a two-part tool for diagnosing flaky network paths. The server runs at the far end and echoes test traffic. The client runs where the problem is seen, measures round-trip latency, packet loss, jitter, connection stability and throughput, and shows the results live in a terminal window or writes them to files for a ticket. Both parts are single executables with no installer and no runtime dependencies.

It speaks the same test protocol over four transports, WebSocket (ws), WebSocket over TLS (wss), raw TCP and UDP, so you can tell apart "the network drops packets" from "the proxy kills WebSocket connections" from "TLS negotiation is slow" using one tool. For devices that cannot run software, such as IP phones, switches and gateways, the client also probes with ICMP ping, TCP connect, SIP OPTIONS and HTTP(S), with the same statistics, chart and reports (section 8).

New in 1.1.0: the client can run as a monitoring service that watches any number of endpoints around the clock and sends an ntfy, Slack, Discord or Microsoft Teams message when one goes down and when it comes back (section 9).

2. Server: settings and operation

Start the server with no arguments for the interactive view, or with --no-tui to log to the console (for services, scheduled tasks and SSH sessions). Every setting is available as a command-line switch, as an environment variable, or in the saved configuration file. Precedence is switch, then environment variable, then configuration file, then built-in default.

nettest-server
nettest-server --no-tui --token s3cret --log-file C:\logs\nettest-server.log
nettest-server --bind 172.16.89.25 --ws-port 9100 --tcp-port 0 --udp-port 0 --wss-port 0

TLS (wss) and the fingerprint

When the wss listener is enabled the server creates a self-signed certificate on first start and prints its SHA-256 fingerprint in the log and in the view, for example:

wss certificate fingerprint (SHA-256): 6A:52:9B:B2:36:96:47:06:FB:F0:AC:7A:EE:A2:A7:CF:49:9D:89:45:D9:1C:9B:FE:3A:51:BD:52:21:9F:67:ED

Give that string to client operators. The client pins it with --fingerprint (or the "TLS: pinned SHA-256" field), which proves the client reached the right server even without a CA. The alternative, --insecure, accepts any certificate and should only be used on a trusted test network.

Scanner identification

Security scanners (nmap, Nessus, Qualys and the like) must be able to identify every listening port. Anything that connects to a nettest listener without speaking the nettest protocol therefore receives a readable answer:

What connectsWhat it receives
An HTTP request on the TCP, ws or wss port (a browser, curl, an HTTP scanner)HTTP/1.1 200 OK with a text/plain body:
nettest by Slaytons Technology Services (nettest-server 1.1.2)
Any other bytes, or a connection that sends nothing for 3 seconds (nmap's "null probe")The same line without HTTP framing, then the connection is closed
A UDP datagram that is not a nettest frameThe same line as one datagram, at most once per source address every 2 seconds and 50 per second overall, so the server cannot be abused to amplify traffic
A TLS client on the wss port that never completes the handshakeThe server certificate, which already identifies the service

Real clients are not affected: the first bytes are inspected and then handed to the protocol handler unchanged. Every banner reply is logged as [scan] <protocol> <peer>: banner sent, which also makes scan activity visible. To check a server quickly: curl http://<host>:9100/.

Security notes

With a token set, unauthenticated TCP and WebSocket clients receive an error and are disconnected; unauthenticated UDP packets are silently dropped, so the server cannot be used as a traffic reflector. The banner reply is the one exception and is rate-limited as described above.

A server installed as a service must have a token. Use --generate-token to create one and distribute it to client operators; set it on clients through NETTEST_TOKEN rather than on the command line where possible.

The server never executes anything from a client and exposes no files; it only echoes test frames and counts bytes.

Server exit codes: 0 clean shutdown, 1 interactive view error, 2 could not bind a port, 3 bad arguments or configuration.

3. Server: running as a system service

For a permanent test endpoint the server installs itself as a systemd unit on Linux or a Windows service, starting at boot with fixed, pre-determined settings. All of this is done by the executable itself; no unit files or sc.exe commands need to be written by hand.

nettest-server service install --token <secret>                      # all four listeners, default ports
nettest-server service install --generate-token --ws-port 9100 --tcp-port 0 --udp-port 0 --wss-port 0
nettest-server service edit --idle-timeout 120 --wss-port 9102        # change settings and restart
nettest-server service status
nettest-server service stop | start | restart
nettest-server service uninstall       # add --purge to delete the server's settings, certificates and logs too
SubcommandWhat it does
install [settings]Copies the executable to the system location, writes the settings file, registers the service to start at boot and starts it. Accepts every server switch from section 2 plus --generate-token, --no-copy (run from the current location instead of copying) and, on Windows, --account. Re-running install replaces the settings but keeps an existing token unless a new one is given.
edit [settings]Applies the given switches to the stored settings and restarts the service. Only the switches you give change. The token can be replaced (--token, --generate-token) but not removed.
uninstall [--purge]Stops and removes the service and the copied executable. --purge also deletes the server's settings, certificates and log files, and nothing else: a client monitor installed on the same machine (section 9) keeps its files.
start, stop, restartControl the installed service.
statusShows whether the service is installed and running, the stored settings (token masked), the wss fingerprint and where the log is. Needs no elevation.

A token is mandatory. install refuses to continue (exit code 3) when no token is given through --token, the NETTEST_TOKEN environment variable or --generate-token. A generated token is printed exactly once, marked "copy it now"; store it in your password manager and give it to client operators. edit accepts a new token but never an empty one, so an installed service can never be opened up by mistake.

Administrator rights

Every subcommand except status needs root or administrator rights, and the installer obtains them itself. On Linux it re-runs through sudo (or pkexec / doas when sudo is absent), so the password prompt and all output appear in the same terminal. On Windows it triggers the User Account Control prompt; the elevated run happens in the background and its output is shown in your window when it finishes. Declining the prompt ends the command with exit code 3. Running from an already elevated shell skips the prompt.

4. Client: interactive terminal UI

Run nettest-client with no arguments, or with a target URL to pre-fill the form, for example nettest-client ws://10.0.0.5:9101. The client moves through three screens:

Settings  --(s)-->  Running: stats | live chart | log  --(x)-->  Summary

Settings screen

All test settings are edited here. Text fields are edited with Enter (type, then Enter to commit or Esc to cancel). Toggles flip with Enter or Space; choice fields such as protocol cycle through their options. Invalid values are refused with a message on the status line. Fields that have no effect with the chosen protocol or mode (for example the token with ping, or the throughput fields in latency mode) are shown dimmed and their hint says so. The field reference is in section 5.

Running screen

Stats panel (left): sent/received, lost with percentage, late/out-of-order/duplicate counts, in-flight probes, last RTT, min/avg/max, p50/p95/p99, jitter. Soak runs add disconnects, reconnects, uptime, longest outage and session length. Throughput runs show instantaneous and per-direction Mbit/s.

Chart (right): RTT over time as a line, with red markers along the baseline where probes were lost. In throughput mode it plots instantaneous Mbit/s. Keys 1 2 3 switch the window between the last 60 seconds, the last 5 minutes and the whole run.

Log panel (bottom): connection events, every failed probe, reconnect attempts and errors. With "Log failures only" off it also lists every successful probe.

Header: target, mode, link state (connected, disconnected, reconnecting #n; for serverless probes "disconnected" means an outage is open) and elapsed time.

Summary screen

Shown when the run ends. It lists the final statistics, connection-phase timings, stability events, and the path of the HTML report if one was written. From here you can run again with the same settings or go back to the settings screen.

Target shorthand

The first positional argument sets protocol, host and port at once: wss://edge.example.com:9102, udp://10.0.0.5:9100, [fd00::5]:9101, or just 10.0.0.5. Serverless targets: ping://10.0.0.77, connect://10.0.0.77:5060 (the port is required), sip://10.0.0.77, https://10.0.0.77/admin. The same forms are used for targets in the monitor's configuration file (section 9). A device literally named monitor or service needs a scheme (ping://monitor) so it is not taken for the subcommand of the same name.

6. Client: headless and scripted use

Add --no-tui to run without the interactive view. The client prints events to the console, writes whatever files are enabled, prints a summary at the end, and returns an exit code that scripts can act on. This is the mode for scheduled tasks, cron, remote shells and one-off checks from a script. For continuous watching with alerts, use the monitor (section 9) instead of a loop around headless runs.

# Five minutes of 100 ms probes over wss, CSV + JSONL + HTML report into C:\runs
nettest-client --no-tui wss://edge.example.com:9102 --fingerprint 6A:52:9B:... ^
    -i 100ms -d 5m --csv --jsonl --report -o C:\runs
# Overnight stability check: heartbeat every 5 s for 8 hours, log every disconnect and reconnect
nettest-client --no-tui ws://10.0.0.5:9101 -m soak --heartbeat 5s -d 8h --text
# Throughput, 10 seconds each direction
nettest-client --no-tui tcp://10.0.0.5:9100 -m throughput --tp-secs 10
# Scripted check: fail if loss exceeds 1% or p95 exceeds 80 ms, one JSON line on stdout
nettest-client --no-tui udp://10.0.0.5:9100 -i 50ms -c 600 --max-loss 1 --max-p95-ms 80 ^
    --json-summary --quiet --no-report
# An IP phone with no server behind it: SIP OPTIONS every 10 s overnight, CSV and report
nettest-client --no-tui sip://10.0.0.77 -m soak --heartbeat 10s -d 8h --csv --report

On Linux use \ instead of ^ for line continuation.

SwitchPurpose
--max-loss <pct>Exit 1 if loss is above this percentage. Default 0, so any loss fails the run.
--max-p95-ms <ms>Exit 1 if the p95 round-trip time is above this value.
--json-summaryPrint the final summary as one JSON object on standard output instead of the text table. Everything else goes to standard error.
--quietSuppress per-probe and event console output.
--all-samplesPrint every probe to the console, not only failures.

Exit codes

7. Test modes and what they measure

ModeWhat happensWhat you get
latencyThe client sends numbered probes at a fixed interval; the server echoes each one back.Round-trip time min/avg/max and p50/p95/p99, jitter, loss percentage, late replies, out-of-order and duplicate counts.
soakOne long-lived connection with periodic heartbeats. If it drops, the client reconnects with increasing back-off and keeps going.Every disconnect with its reason, reconnect attempts and downtime per outage, uptime percentage, longest outage, longest unbroken session, plus the same RTT statistics from the heartbeats.
throughputThe client streams data to the server for N seconds, then the server streams back for N seconds (or one direction only).Mbit/s, bytes and frame counts per direction. On UDP, the percentage of datagrams that never arrived.

All modes record the connection phases for every connection attempt: DNS lookup, TCP connect, TLS handshake, WebSocket upgrade and the authentication exchange, each timed separately. Phases that do not apply to the protocol are shown as a dash.

How loss is decided. A probe is counted as lost when no echo has arrived after 2 seconds or ten probe intervals, whichever is longer. If the echo turns up later it is moved from "lost" to "late", so slow links are reported as high latency rather than as loss. (The monitor uses its own per-target timeout instead, section 9.)

Failed is not lost. When the far end answers negatively before the timeout (TCP connection refused, ICMP host unreachable) the probe is recorded as failed with the reason, instead of waiting out the timeout. Failed probes are included in the loss percentage so thresholds behave the same; the summary shows the split.

Round-trip only. RTT is the time from sending a probe to receiving its echo, measured on the client's own clock. The server adds nothing from its clock, so the two machines never need synchronised time. One-way latency is therefore not reported.

8. Testing devices without a server

Many stability complaints concern devices that cannot run nettest-server: desk phones, conference units, switches, access points, printers, gateways. The client tests them directly with a protocol the device already speaks. Pick the scheme in the Protocol field or the target URL; everything else (interval, duration, soak mode, logs, chart, HTML report, exit codes) works as for a nettest-server target.

SchemeWhat is sentWhat counts as an answerNotes
pingICMP echo request, size from "Frame size" (default 64 bytes).The matching echo reply.No port. Unprivileged on Windows and on Linux systems that allow ping sockets (all common distributions); otherwise run as root or use connect. Some devices rate-limit ICMP; keep the interval at 200 ms or slower.
connectA TCP handshake to the given port, closed immediately with a normal FIN.Handshake completed. "Connection refused" (host up, port closed) is reported as failed, distinct from a timeout (host or path down).Port is required (connect://phone:5060). Works against any open TCP port, including the nettest-server ports.
sipA SIP OPTIONS request over UDP (default port 5060), the standard keep-alive that phones, PBXs and SBCs answer.Any final SIP response (200 OK, 401, 405, 486...) whose CSeq and Call-ID match the request. The status line is kept as the sample detail.Tests the phone's SIP stack, not just its IP. Phones that disable OPTIONS show 100% loss; use connect://phone:5060 then. SIP over TCP is not probed.
http / httpsA HEAD request for the path (default /) with a Host header, timed to the first line of the response.Any HTTP status line, including 401 and 404 (the web stack is up). The status line is kept as the sample detail.https accepts any certificate (devices use self-signed ones) unless a fingerprint is pinned. The RTT includes connect and, for https, the TLS handshake.

Stability without a connection

Serverless probes have no connection to lose, so soak mode derives stability from the probes themselves: when Outage after N failures (default 3) consecutive probes fail or go unanswered, an outage opens and is logged with the reason; the next answered probe closes it and the downtime is recorded. Disconnect count, uptime percentage, longest outage and longest unbroken session are then reported exactly as for a nettest-server soak, and the header shows "disconnected" while an outage is open. The heartbeat interval is the probe interval in soak mode.

What is the same, what differs

Same: RTT min/avg/max, percentiles, jitter, loss %, the live chart with loss markers, console/CSV/text/JSONL logs, the HTML report, --max-loss / --max-p95-ms thresholds and exit codes.

Connection phases show only DNS (and the peer address); there is no TLS, WebSocket or authentication phase to time.

A new status fail appears in logs and CSV for refused/unreachable answers, with the reason in the detail column. "Late" cannot occur: an answer after the timeout is discarded.

On Linux an ICMP "destination unreachable" for ping is not delivered to unprivileged sockets, so an unreachable host appears as timeouts (as with the ping command). Windows reports it as failed.

Throughput mode is not available: there is nothing on the far end to send or receive bulk data.

Examples

# Is the phone there, and how is the path to it? 120 pings, one every half second
nettest-client --no-tui ping://10.0.0.77 -i 500ms -c 120
# Is its SIP port reachable through the night? Outage after 2 missed probes
nettest-client --no-tui connect://10.0.0.77:5060 -m soak --heartbeat 5s --outage-after 2 -d 10h --csv
# Does the SIP stack answer, and how fast? Status lines in the CSV detail column
nettest-client --no-tui sip://10.0.0.77 -c 60 -i 1s --csv --all-samples
# The device's web interface, self-signed certificate accepted
nettest-client --no-tui https://10.0.0.77/ -c 20
# Interactive: pre-filled, then press s
nettest-client sip://10.0.0.77

9. Client: monitoring endpoints as a service

nettest-client monitor turns the client into an always-on watcher. It probes any number of endpoints continuously, decides when each one is DOWN and when it is UP again, and sends a message to ntfy, Slack, Discord or Microsoft Teams on every change. Installed as a service it starts at boot and keeps going through reboots, endpoints that are down when it starts, and webhook endpoints that are temporarily unreachable. It uses exactly the probes from sections 7 and 8, so anything you can test you can monitor: a nettest-server across a WAN link, a PBX, a gateway, a printer's web interface.

Typical use: one monitor per site, watching the things that site depends on, telling the on-call phone within seconds when the link to head office, the SIP trunk or the gateway stops answering, and again when it recovers, with the time it was down.

Workflow

nettest-client monitor --example-config > monitor.toml      # annotated template; edit targets and webhooks
nettest-client monitor --config monitor.toml --check        # validate, list what would be watched
nettest-client monitor --config monitor.toml --test-notify  # one test message to every notifier
nettest-client monitor --config monitor.toml                # run in the foreground (Ctrl-C stops it)
nettest-client service install --from monitor.toml          # install and start the service (asks for root / UAC)
nettest-client service status

nettest-client service uninstall [--purge]                  # --purge also removes monitor.toml and the log

The file's encoding is detected and converted automatically: UTF-8 (with or without a byte-order mark), UTF-16 (which is what Windows PowerShell's > redirection writes) and Windows-1252/ANSI (what Set-Content and old Notepad write) are all read. --check prints an encoding line and a warning when a conversion happened, and service install always stores the installed copy as UTF-8, also when re-installing without --from. Run --check and --test-notify before installing: the first catches typos in the file, the second proves the webhook URL, token and TLS path work from this machine. Both exit 0 on success.

The configuration file

monitor.toml has one [monitor] section, one [[targets]] block per endpoint and one [[notify]] block per destination. Durations are written with a unit: 500ms, 10s, 2m, 1h30m; "0" disables a timer. A minimal file:

name = "gateway"
target = "ping://10.0.0.1"          # any target form from section 5
interval = "5s"
timeout = "2s"
failures_before_down = 3            # DOWN after 3 consecutive failures (about 15 s here)
successes_before_up = 1             # UP on the first success
remind_every = "1h"                 # repeat the DOWN alert hourly while still down; "0" = never

[[targets]]
name = "pbx"
target = "sip://pbx.example.com"

[[targets]]

target = "wss://edge.example.com:9102"
token = "s3cret"
fingerprint = "6A:52:9B:..."        # or insecure = true

[[notify]]

[[notify]]

The alert rule

Every probe is a success or a failure. For ws, wss, tcp and udp a lost connection and each reconnect attempt that fails also count as failures, and a successful reconnect as a success. A target becomes DOWN after failures_before_down consecutive failures and UP again after successes_before_up consecutive successes. Anything shorter than that never produces a message, so a single dropped ping is invisible by design. The time to an alert is therefore roughly failures_before_down × interval plus one timeout: with the defaults (10s, 5s, 3) a dead host is reported about 35 seconds after it stopped answering; with interval = "2s", timeout = "2s" it is 8 seconds.

An endpoint that is already down when the monitor starts is reported DOWN after the same number of failures ("already down when the monitor started" in the text). An endpoint that is healthy at start is not announced at all, so a reboot of the monitor machine does not produce a burst of "UP" messages; set notify_on_start if you want to hear from it. While a target stays down, remind_every repeats the alert with the accumulated downtime.

What the messages look like

nettest: gateway DOWN
gateway (ping://10.0.0.1) is DOWN since 2026-10-05 14:03:11 -05:00 after 3 consecutive failures:
probe lost (no reply) — monitor on branch-pc

nettest: gateway UP
gateway (ping://10.0.0.1) is UP again at 2026-10-05 14:09:40 -05:00 after 6m29s down — monitor on branch-pc

nettest: pbx still DOWN
pbx (sip://pbx.example.com:5060) has been DOWN for 1h00m: timed out — monitor on branch-pc

The first line is the title (ntfy notification title, bold in Slack and Discord, the heading of a card in Teams, coloured red for DOWN and green for UP); the rest is the body. The reason is the last failure seen: "probe lost (no reply)", "connection refused", "closed by peer", "reconnect attempt 3 failed: ...". All configured notifiers receive every message. Delivery runs in its own task so a slow webhook never delays probing: three attempts per message (after 2 s and 5 s; a 429 answer is retried after the time the service asks for), a 4xx answer other than 408 and 429 is treated as permanent (a wrong URL will not fix itself), and every outcome is written to the log.

The log

The monitor writes one line per transition, per delivery result and (every summary_every) per target, so the log alone tells the story even if the webhooks were unreachable. In the foreground the log goes to the console; as a service to the file in the table below (and, on Linux, to journalctl -u nettest-monitor).

Running it as a service

nettest-client service install --from monitor.toml validates the file, copies it to the system location, copies the executable, registers the service to start at boot and starts it. The installed file is the only one the service reads; to change anything edit it there (or edit your copy and run install --from again) and run nettest-client service restart, which checks the file before restarting so a typo does not leave you without monitoring. Administrator rights are obtained exactly as for the server (section 3): sudo on Linux, the UAC prompt on Windows, and status needs none.

10. Exports and log files

Files are written to the output directory (default: the current directory) and named nettest-<YYYYMMDD-HHMMSS>.<ext>. Each switch accepts an optional explicit path instead, for example --csv run1.csv.

OutputFileContent
ConsolescreenHeadless only. One line per failed probe plus every event (connect, disconnect, reconnect, result). --all-samples lists every probe; --quiet silences it.
CSV.csvOne row per probe and per event. Columns: timestamp, elapsed seconds, kind, sequence, status (ok/lost/late/ooo/dup/fail), RTT ms, running loss %, p50, p95, p99, jitter, detail (failure reason, or the SIP/HTTP status line for serverless probes; event text for events). Opens directly in Excel.
Text log.logThe same lines as the console, honouring "log failures only".
JSON Lines.jsonlOne JSON object per probe and event, for Splunk, Elastic, Loki and similar.
HTML report.htmlSingle self-contained page: summary tiles, RTT chart with loss markers, throughput table, stability events, connection-phase table and the event log. No JavaScript and no external resources, so it opens offline and is safe to attach to a ticket or e-mail.
Server logany--log-file and --jsonl on the server record each client's connect, disconnect reason and per-session totals, plus every [scan] banner reply: the server-side half of the evidence. For a service the log is at the location in section 3.
Monitor logmonitor.logEvery DOWN / UP transition with its reason, every webhook delivery or failure, and a periodic status line per target (section 9). jsonl_file gives the same as JSON Lines. The monitor writes no per-probe files.

In the interactive view the HTML report is written automatically when a run ends (if the toggle is on) and can also be written at any moment with r. The report path is shown on the status line and the summary screen.

11. Reading the results

FigureHow to read it
last / min / avg / max RTTRound-trip time in milliseconds. On a LAN expect well under 1 ms; across a WAN tens of ms. Max alone is not alarming; a max far above p99 is a single spike.
p50 / p95 / p99Percentiles. p95 = 25 ms means 95% of probes returned within 25 ms. These describe what users feel better than the average: a path that is usually fast but stalls once a minute has a fine average and a bad p99.
jitterSmoothed variation between consecutive RTTs (the estimator used by VoIP). Steady 50 ms is fine for voice; 10 ms that swings by 30 ms is not.
lost / loss %Probes with no echo. On TCP and WebSocket this is rare because the transport retransmits; loss there shows up as RTT spikes instead. UDP shows true packet loss.
failedProbes answered negatively (connection refused, host unreachable). Part of the loss count. Many failures with "connection refused" mean the host is up but the service on that port is not.
lateEchoes that arrived after the loss timeout. Many late replies mean a very slow or congested path rather than a lossy one.
ooo / dupOut-of-order and duplicate echoes. Common on UDP across multi-path links; on TCP they indicate something unusual in the path.
in flightProbes sent but not yet answered. A climbing value during a run means the path has stalled.
Connect phasesDNS, TCP, TLS, WS upgrade, hello. Whichever is large is where the delay lives: resolver, network, certificate handling, or a proxy.
Soak: disconnects, uptime, longest outageHow often the connection died, how long it stayed dead, and how long it stayed up. Downtime per event is in the HTML report and logs.
Throughput Mbit/sPayload bits per second on the wire for that direction. Compare upload with download from the same run.
Monitor: DOWN / UP, "after 6m29s down"The downtime in an UP message is measured from the moment the target was declared DOWN, so it is shorter than the real outage by about the detection time. The periodic summary line gives the loss % and p95 since the monitor started, for the "it is up but bad" cases an alert cannot express.

12. Troubleshooting recipes

SymptomWhat to run and what it tells you
Application disconnects every few minutesSoak over the application's protocol with the heartbeat at, say, 30 s. Disconnects at a regular interval point at a NAT, firewall or load-balancer idle timeout. Lower the heartbeat below that interval; if the drops stop, keep-alives are the fix.
Calls or video are choppyUDP latency test at 20 ms interval for a few minutes. Look at loss %, jitter and p99. Loss and jitter on UDP are what real-time traffic experiences.
"The network is slow"Latency test over TCP and over ws. Check the connect phases first: high DNS means the resolver, high TCP means the path, high TLS or WS upgrade means a middlebox or certificate issue. Then look at p95 and p99 rather than the average.
WebSocket app fails but the website loadsRun ws and tcp tests to the same server. TCP fine and ws failing with a TCP time but no WS-upgrade time means a proxy or load balancer refuses the upgrade.
Transfers are slow in one directionThroughput mode with direction "both". A large asymmetry between upload and download usually means traffic shaping or a duplex mismatch.
Loss on UDP but not on TCPThat is genuine packet loss. TCP hides it by retransmitting, which appears as RTT spikes and a high p99 in the TCP test.
Client exits with code 2 immediatelyWrong port or protocol for the server's listener, firewall blocking the port, token mismatch, or a wss fingerprint that does not match. The console line before the summary says which.
A phone keeps losing registrationRun sip://phone -m soak --heartbeat 10s from the same network segment overnight. Outages that coincide with the drops put the fault on the network or the phone; a clean run points at the PBX or the trunk, which you test with connect://pbx:5060 or a nettest-server next to the PBX.
Devices on a switch "disappear" brieflyping://device -m soak --heartbeat 1s --outage-after 3 against two or three devices on that switch at once. Simultaneous outages are the switch or its uplink; a single device alone is that device.
"Tell me when the branch loses the head office"Install the monitor (section 9) on a machine at the branch with ping:// or connect:// targets for the head-office gateway and a wss:// target for a nettest-server there, plus an ntfy topic on the on-call phone. The DOWN message arrives seconds after the link dies, the UP message says how long it was gone.
Monitor alerts never arrivenettest-client monitor --config monitor.toml --test-notify on the monitor machine. The log line says exactly what the webhook answered: a 404 or "no_service" is a wrong URL, a 401/403 a bad token, "timed out" a firewall or proxy between the machine and the endpoint, a TLS error a self-hosted ntfy without insecure or fingerprint. As a service, read the monitor log: every delivery attempt is recorded there.
Monitor alerts too often for a flaky but working endpointRaise failures_before_down or lengthen interval so a single lost probe cannot trigger; raise successes_before_up so one lucky reply does not end an outage. Use remind_every instead of a short interval if you only want to be nagged while it stays down.
A ping:// target is always DOWN in the monitor but nettest-client ping:// worksRun the monitor in the foreground as the same user: the log's first lines say why probing cannot start. On Linux the installed service already has the raw-socket capability; on an older kernel or a hardened sysctl use connect:// to a known port instead.
ping:// reports ICMP not permittedLinux only: the account's group is outside net.ipv4.ping_group_range. Run as root, widen the range, or use connect://host:port.
A vulnerability scan flags an unknown service on 9100-9102That is nettest-server; open http://host:9100/ in a browser to see the identification banner. The text is configurable with --banner if the scanner needs a particular string.
Need evidence for a carrier or vendorRun headless with --csv --report for the agreed period and attach the HTML report; it contains the chart, every event, and the per-phase timings in one file. For an outage history over weeks, the monitor log lists every DOWN and UP with timestamps and durations.
